# 資源の選択とRの因果｜S6～S10追補

**A=0。全て10/6固定BuildソースのB、または実試遊が必要なC。** 表はコードを読み、成立条件を置いて計算した状態追跡であり、内部APIを実行した結果でも通過記録でもない。操作難度・面白さ・所要時間は決めない。

## 新しく確かめたこと

1. CP補充は「残量を下限まで引き上げる」。最大50への全回復でも、指定数の加算でもない。指定長の追跡ではS6の14差はCP7で保たれ、CP9で12差へ縮む。**節約の意味が全て消えるという評価は不正確。**
2. E接続・解除は残量を使わず、Qで橋へ確定した時だけ選択した接続長を使う。Fは既存2本の長さを合算し、消費も返却もしない。メソッド名`DetachAndRefund`を返却の証拠にしない。
3. Rの境界は「直近の受理済みCP」。補充後の残量を保存するため、Rで補充前へ戻るわけではない。橋・除去した中央フックも同じ境界で戻る。
4. 「選べる長さ」と「その長さでQできる」は別。S10入口残量11では選択11が可能でも、最低残量1を残す条件によりQ11は不可。端点間9なので資源と長さの条件だけでは9/10が候補になる。通行可能な曲線かは別確認。

根拠本文：[行番号付き抜粋](evidence/resource-retry-source-excerpts.md)。照合した15入力は全て[BuildInputsとハッシュ一致](evidence/resource-retry-source-hashes.json)。以前の29件・追補16件と重複があり、合算してユニーク件数とはしない。

## 状態を混ぜないための定義

| 状態/操作 | コードで確認できた意味 | 評価に用いない読み替え |
|---|---|---|
| 残量R | `RopeResource.CurrentLength`。Main通常開始は保存Sceneの最大50へreset | 選択長と残量を同じものにしない |
| W/Sの選択長L | 未接続時に変更。上限は`max(1,floor(min(14,R)))` | 長さ8を選んだだけで8消費したとはしない |
| E接続・解除 | 接続長を確定するが残量は減らない。解除で残量増加の処理もない | 「振り子を使うたび減って返る」と説明しない |

| F | 未接続で2本が接する中央を狙い、合計長の1本へ作り替え中央を除く | ヒモの回収や追加消費とはしない。S3のFスイッチは別機能 |

## CP成立の前提

床の端に触れるだけでは保存成立とは言えない。MainStageCheckpoint25–42からLandingGateを経て、上面支持・接触位置・相対縦速度等の条件と、定数0.12秒の継続支持を確認する。その上でヒモ未接続かつ先の区間番号である必要がある（MainStageRespawn183）。0.12秒はコードの判定定数であり、今回待った時間ではない。

受理後の表示コードは「第{区間}区間」「復帰地点を更新」（SectionArrivalFeedback58/119）。ここには補充量の専用文はないが、他のHUD更新もあるため「プレイヤーは補充に気付けない」とは断定しない。

### 補充が差を縮める反例

上の表は先行消費を固定した一例であり、常に14差が残る仕様ではない。仮にS6入口が両方34なら、上Q14で20→CP7補充25、下34はそのまま。差は9。その後Q4→CP9では上21→23、下30のままで差7になる。先行状態の到達例を今回実証したわけではない。

一般に`max(R,b)`は、両方が下限b以上なら差を保存し、片方だけ下回れば差を縮め、両方とも下回れば差を消す。境界例としてCP9受理直前20と22なら、どちらも23になる。この20/22を作れる攻略経路があるとの主張ではなく、**「補充は必ず差を保存する」への代数的反例**。補充を直ちに削る根拠にはしない。

## S10で節約は何に効くか

残量11では長さ11も選択上限内だが、Q11は最低1を残せず不可。端点間距離9なので、資源/幾何のゲートだけでは9か10が候補。残量23なら選択上限14となり、9～14はそのゲートを満たす候補になる。ただし長くするとたわみも増える。**選択肢が増えることを必ず有利・面白いとは扱わない。**

推奨10だけが唯一の許容値ではない。最後の橋を9で作った場合の残量は上2/下14という条件計算になり、元の「上1/下13」を固定したクリア結果として使わない。残量1はMainの枯渇判定`R<1`（保存Scene9739）未満ではなく、その値だけで失敗とは言えない。新たなQで最低1を残す余裕がないことと、失敗を分ける。

S9統合橋の合計長12は、残量が11の状態でも既に橋へ使った分なのでFに追加課金を求めない。橋の長さ12と本人の残量11が同時に見えても、直ちに表示矛盾とはしない。

## S6の「1.5秒」出典と正確な対象

RopeController42の`airChainReconnectWindow=1.5f`はMainStage保存値9761でも1.5。解除したフックがAirChainStepの時に、`Time.unscaledTime + 1.5`を期限にする（335–346）。再接続は同じgroupでorderが直前+1のフックだけ（349–355）。さらに体からフックまでが`min(選択長,14)+0.01`以内であることが必要（358–391）。

S6下のA/B/Cにはgroup`MainS06Lower`とorder1/2/3を設定する（SixSetup32/111–113/222–225）。期限内は通常照準の探索より次のフック探索を使い、空中Eの例外を許す（RopeController509–516）。**1.5秒以内なら任意のフックへ飛べるわけではない。** 時間定数は確認できたが、反応のしやすさ・実際の余裕・音は未評価。

UI U03の主行は秒数を詰めず「S6の下ルートでは、外した直後に次のフックへ掛けられる」とし、必要なら現場の補足へ「解除後1.5秒以内・次のフックが届く距離で」を置く案。通常接続の接地条件は残す。SpaceはcoyoteTime/入力bufferがあるため「接地の瞬間だけ可能」と断定せず、「足場からジャンプ（ヒモ未接続時）」へ直す。

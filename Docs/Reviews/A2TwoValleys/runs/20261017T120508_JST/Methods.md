# 撮影条件・事実と未確認の境界

## 同条件比較

Unity 6000.3.21f1、A2 B、入口24／6／0、同じ背景・地形・Camera・解像度1280×720。原画像をUnityのScreenCaptureで取得し、JPEG表示用プレビューと動画へ変換した。比較ラベルは画面外、3倍cropは補助と明記。画像生成・ゲーム画面内への描き足し・正解ルート描画は行っていない。

入力は撮影用A2InputDriverが既存のPlayerMoverフィールドへ渡し、接続・解除・橋・Rは既存APIで操作。Rootの診断配置、力・速度・Joint・入力方式・地形の変更で成功させていない。既存A2の起動時入口配置／CP設定はそのまま残る。

描画前にも同じ撮影用入力値を反映する。元driverはFixedUpdateだけを書き換えるため、その後のPlayerMover.Updateで中立OS入力へ戻り、描画側は0を読んでいた。**今回の撮影条件訂正であり、手動版の入力ルール変更ではない**。候補2にも同じ訂正を適用。候補2の表示計算自体は変更せず、以前の自動動画とのpixel同一とは主張しない。

## Build・記録の履歴

1. r1：Compile／Build成功。非表示ウィンドウの撮影が黒画像となり、比較証拠に不採用。元記録は削除しない。
2. 同じr1を通常表示して画面取得に成功。描画側の入力が0となる問題を確認したため、これを最終の加速／制動証拠にはしない。
3. r2：撮影用入力の描画反映、共通開始時刻、JPEG保存を整備。主比較と左右空中頂点を両候補で収録。
4. r3：演出を変えず、短い加速／逆入力／入力なしの補助ケースだけ追加。補助撮影と最終手動版に使用。コンパイル済みPDBのSource checksumで、r2／r3差分はConnectionGestureCaptureだけ。[照合](QA/BetweenBuildsCompiledSources.json)。

一度、補助撮影の実行承認が時間切れになり、起動されなかった。同じ許可済み隔離対象で1回だけ再試行して収録した。ゲームの失敗・sky失敗へ読み替えない。

## 時間・画像

主動画6.47秒、自由な左右頂点3.13秒、入力補助1.77秒。30fpsのオフライン時計をゲーム内時間の等速としてencode。収録時の壁時計時間や通常実行時のFPSとは異なる。無音。手動起動は `captureFramerate=0` の通常実時間、元の音を保持。

ポーズはAPIによるtimeScale停止でありEsc実キーではない。壁時計0.3秒の停止中の描画フレーム数が候補2で5、新候補で6となったため、主な軌道比較はその前の318フレームで照合し、停止自体は各記録内で姿勢保持を確認。ポーズ後のフレーム番号を機械的に1対1と扱わない。

主動画の大きい往復には旧地形への接触を含みうるため、空中頂点の証拠は小振幅の自由区間を別に使う。ここでは接地0、入口床の側面からもCollider幅を含めて離れている。[遷移](QA/Transitions.json)。

解除後・R後のJSONに残る手の座標は、非表示前の最後の値を保持するフィールド。weight0／非表示を「腕の残骸」と誤読しない。実画面のR後画像も併記した。

## 未確認

Human／CodexのOS実キー、音の実聴、メニューを含む実Esc、全区間・全Hook・全残量・F統合の追加検証、実操作感、面白さ、正式採用。Unity内部の自動入力をHuman操作へ言い換えない。

手動版の35秒観測後は検証シェルが自分で起動した新exeのPID／絶対パスを照合して終了した。ゲーム内の自動終了ではない。旧候補・Human試遊・ponのプロセスは停止しない。
